# Liverpool Gaming — API المالية والأمان

## ما تم تنفيذه
- إضافة جداول منفصلة للمخزون، فواتير البيع وبنودها، حركات المخزون، وحركات الخزنة.
- `POST /api/finance/sales`: ينفذ البيع داخل معاملة PostgreSQL واحدة، يقفل صفوف الأصناف، يتحقق من الفرع والرصيد، يقرأ السعر والتكلفة من الخادم، ويكتب الفاتورة وبنودها وخصم المخزون وحركة الخزنة معًا. يستخدم مفتاح idempotency لمنع تكرار البيع عند إعادة المحاولة.
- `POST /api/inventory/items`: إضافة/تحديث بيانات صنف من صلاحيات المالك/الإدارة/المشرف.
- `POST /api/inventory/adjustments`: تعديل المخزون داخل معاملة، مع منع الرصيد السالب ومفتاح منع التكرار.
- `POST /api/finance/cash-transactions`: قيد مصروف/سلفة/سحب/تسوية/تحصيل بدور وصلاحيات محددة ومفتاح منع التكرار.
- `POST /api/auth/bootstrap-owner`: يربط أول حساب Supabase Auth بدور owner مرة واحدة. فهرس فريد يمنع إنشاء مالكين متزامنين.
- `GET /api/auth/me`: يعيد هوية العضو والدور بعد التحقق من جلسة Supabase.
- جميع جداول العمليات المالية محمية بـ RLS ومن دون سياسات مباشرة لـ anon/authenticated؛ الوصول من خلال خادم التطبيق فقط.

## إعداد الخادم
يحتاج الخادم متغيرات سرية في منصة الاستضافة:
- `SUPABASE_URL`
- `SUPABASE_PUBLISHABLE_KEY`
- `DATABASE_URL` (سلسلة اتصال PostgreSQL الخاصة بالخادم فقط)
- `PORT=3001`

لا تضع `DATABASE_URL` أو أي service-role/secret key داخل الواجهة أو ملف ZIP. مفتاح publishable وحده ليس سرًا ويمكن استخدامه من الواجهة.

## نقاط تمنع إعلان الجاهزية للإنتاج حاليًا
1. واجهات React الحالية ما زالت تنفذ بعض عمليات البيع والمخزون والخزنة في الحالة المحلية. وجود endpoints لا يعني أن كل الأزرار في الواجهة تستخدمها بعد؛ يلزم ربط الواجهة بالطلبات غير المتزامنة وعدم تأكيد العملية قبل رد الخادم.
2. تسجيل الدخول المحلي القديم بالهاتف وPIN ما زال موجودًا في الواجهة. يجب تحويله إلى Supabase Auth (بريد/كلمة مرور أو مزود هوية معتمد) واستبدال الصلاحيات المحلية بالهوية التي يرجعها `/api/auth/me` قبل نشر النظام.
3. يجب إنشاء حساب المالك الأول من شاشة إعداد فعلية أو عبر Supabase Auth ثم استدعاء `/api/auth/bootstrap-owner`. لا يوجد مالك مضاف تلقائيًا الآن.
4. جدول المخزون المالي الجديد منفصل عن مصفوفة `lg_inventory` القديمة. يلزم استيراد الأصناف الموجودة ومراجعة الأرصدة والأسعار قبل استخدام البيع المالي على بيانات حقيقية.
5. لم تكتمل اختبارات المتصفح/الاختبارات التكاملية في هذه البيئة: تثبيت npm dependencies انتهى بمهلة/تعذر، لذلك لم يمكن تشغيل Vite أو Express end-to-end. فحص بناء جملة Node نجح فقط. لا تعتبر النسخة جاهزة للتسليم الإنتاجي قبل نجاح `npm ci`, `npm run lint`, `npm test`, `npm run build` واختبارات بيع حقيقية في بيئة staging.

## اختبار التكامل المطلوب في staging
- طلب بلا Bearer token → 401.
- مستخدم Auth بلا عضوية فعالة → 403.
- دور غير مسموح لتعديل المخزون/الخزنة → 403.
- بيع لصنف غير موجود/فرع آخر/مخزون غير كافٍ → لا تتغير أي بيانات.
- بيع متعدد الأصناف → الفاتورة والبنود والمخزون والخزنة تُحفظ جميعها أو لا يحفظ أي منها.
- تكرار نفس idempotency key → لا تتكرر الفاتورة أو الخصم.
- عمليتا بيع متزامنتان على آخر وحدة → واحدة فقط تنجح.
- تعديل مخزون يؤدي إلى رصيد سالب → مرفوض.
- تأكد أن الواجهة لا تعرض نجاحًا عند انقطاع الشبكة أو 4xx/5xx.
